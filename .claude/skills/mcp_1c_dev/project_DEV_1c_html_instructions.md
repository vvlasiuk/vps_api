# Інструкції проєкту: розробка vps_api

Ти допомагаєш розробляти vps_api — FastAPI-бекенд + статичні HTML-сторінки, що працюють
із 1С 8.3 (УТП) через проміжний HTTP-сервіс. Інтерфейс українською.

MCP-інструменти — джерело правди про систему. Їхні докстрінги описують параметри й
формат відповіді; ця інструкція описує те, чого в докстрінгах немає: політики, процеси,
контракти й тонкощі домену.

## Головні принципи

- Аналізуй мовчки; роби мінімальні, точкові зміни строго в межах задачі.
- Не чіпай коментарі й закоментований код, якщо про це не просять.
- Відповідай стисло, українською.
- Не вигадуй структуру 1С, поля, API компонентів чи вміст файлів — бери через
  `describe_object`, `get_query`, `read_form`, `cf_body`.
- **Твердження про код — лише після перевірки.** Здогад, поданий як факт, гірший за
  визнане «не знаю — перевірю».
- Уникай зайвих елементів UI: якщо кнопка чи поле не має чіткої ролі — не додавай.

## Хто що пише

| Що | Хто застосовує |
|---|---|
| `queries1c/` (.sel/.json) | Claude через `save_query` |
| `html/pages/`, `html/menu/` | Claude через `write_form` |
| Python-бекенд, `server.py` MCP, BSL 1С | **Тільки користувач вручну** |

MCP — єдиний канал запису на диск. **Filesystem — тільки читання**: ні форм, ні запитів,
ні логів. Журнал ведеться виключно через `log_command` (єдине джерело правди щодо
формату — бекенд).

Для файлів, які застосовує користувач, Claude:

- готує **повний текст файла** — не діфи й не фрагменти. Виняток — чистий доклад у
  кінець файла: тоді достатньо блока для дописування;
- короткі шматки (до ~20 рядків) дає в тексті повідомлення, довгі — файлом;
- зберігає **CRLF і відсутність переносу в кінці** (стиль проєкту, Windows) — інакше
  diff покаже «змінено весь файл» замість реальних правок;
- звіряється з поточним станом на диску перед видачею, щоб не затерти чужі зміни й не
  згубити наявні функції.

Filesystem-конектор часто нестабільний (зависає на `list_directory`, тихо падає).
Обхід — `read_text_file` на конкретний шлях, без паралельних викликів після першого
збою. Не «добивай» повторами: попроси користувача вставити код у чат.

## Цикл блоку змін (бекап → зміни → лог)

1. **Бекап** — ПЕРЕД змінами `create_backup`.
2. **Зміни** — `save_query` та/або `write_form`.
3. **Лог** — наприкінці ОДИН `log_command` на всю команду.

- Одиниця логу — **команда користувача**, не окрема операція запису. Одна команда, що
  зачепила і `.sel/.json`, і html — це ОДИН `log_command` з усіма файлами у `files`.
- Кожен елемент `files` — об'єкт `{root, path}`, НЕ голий рядок-шлях:
  - `root` — фіксовано одне з трьох: `"html"` | `"queries1c"` | `"html_command_log"`;
  - `path` — те саме значення, що вже повернули `write_form` (поле `path`) чи
    `save_query` (`path_sel`/`path_json`) — перенось його з відповіді, не набирай
    вручну і не додавай префікс кореня самостійно (`path` вже без нього).
  - Приклад: `[{"root": "queries1c", "path": "catalogs/Контрагенты/cat_contractors.sel"},
    {"root": "html", "path": "pages/contractors/list.html"}]`.
- Для запиту вказуй у `files` ЛИШЕ `path_sel` (root="queries1c") — НЕ додавай окремо
  `path_json`: інакше на одну команду створяться два `.changes.md` сайдкари замість
  одного.
- Пропуск `log_command` буде тихим: ніщо не нагадає. Це обов'язкова закриваюча дужка,
  парна до бекапу.

## Архітектура

```
HTML (компонент) → FastAPI (/1c/query, /1c/save_doc) → 1С HTTP-сервіс (hs/vps/...) → 1С
```

- Дані читаються через ІМЕНОВАНІ запити (`queries1c/`), не сирим текстом.
- Фронт працює з АЛІАСАМИ полів (латиниця), не знаючи структури 1С.
- Бекенд обгортає запит: `ВЫБРАТЬ {fields} ИЗ ( <текст .sel> ) КАК Вложенный`,
  і накладає зверху `fields`/`filters`/`order` по аліасах.

## Система запитів (.sel + .json)

Пара файлів у `queries1c/<catalogs|documents>/<Об'єкт>/`:

- `.sel` — текст запиту 1С (`ВЫБРАТЬ`, `ИЗ`, `ГДЕ`, `КАК`). `//` — коментар.
- `.json` — метадані, **джерело правди**:

```json
{
  "query_name": "<ASCII-ідентифікатор>",
  "object_type": "<Справочник|Документ>",
  "object_name": "<ім'я об'єкта>",
  "source_name": "1C_UTP",
  "info": "<опис українською>",
  "fields": [ {"key": "<аліас>", "type": "<тип>", "info": "<опис>"} ]
}
```

Порядок ключів саме такий: `query_name` згори, `fields` внизу.

**Типи** (`fields[].type`) — СУВОРО одне з: `ref`, `string`, `number`, `date`, `boolean`.
Посилання (`СправочникСсылка`/`ДокументСсылка`/…) → `ref`; `Строка` → `string`;
`Число` → `number`; `Дата` → `date`; `Булево` → `boolean`.

### Перелічення — окремий випадок серед ref-полів

Перелічення технічно теж `kind: "ref"` (`describe_object` показує
`{"kind":"ref","object":"Перечисление.X"}`), але поводиться інакше за
Довідник/Документ-посилання:

- **Читання:** конвертер 1С повертає `{type, presentation, value}` — ідентифікатор у
  ключі **`value`** (`XMLСтрока(Значення)`), а НЕ в `guid`, як для звичайних посилань.
- Тому в `.json` тип поля лишається **`"ref"`**, а НЕ `"string"`: із `"string"` бекенд
  стриже об'єкт до `presentation`, і сирий `value` (потрібний для запису назад)
  губиться безповоротно.
- **Запис:** у payload
  `{type:"ref", value:{type:"Перечисление.ІмяПерелічення", guid: <.value з читання>}}`.
  Ключ `guid` лишається тим самим і для перелічення — це назва параметра функції, а не
  вимога справжнього UUID (`XMLValue` приймає коректний XML-рядок).
- **На фронті:** показ через `.presentation`; запис через `.value` — НІКОЛИ через
  `.guid` (його в перелічення немає) і НІКОЛИ через `.presentation` (людський текст).

### Системні поля (обов'язково, згори `.sel` і `fields`)

Псевдонім таблиці: `дов` (довідник), `док` (документ).

Довідник — завжди:
```
дов.Ссылка КАК _ref (ref), дов.Код КАК _code (string),
дов.Наименование КАК _description (string), дов.ПометкаУдаления КАК _marked (boolean)
```
Довідник — ДОДАТКОВО лише якщо ієрархічний (є `Родитель`/`ЭтоГруппа` в describe):
```
дов.Родитель КАК _parent (ref), дов.ЭтоГруппа КАК _isfolder (boolean)
```

Документ — завжди:
```
док.Ссылка КАК _ref (ref), док.ВерсияДанных КАК _version (string),
док.Номер КАК _number (string), док.Дата КАК _date (date),
ВЫБОР КОГДА док.Проведен ТОГДА 1 КОГДА док.ПометкаУдаления ТОГДА 2 ИНАЧЕ 0 КОНЕЦ КАК _status (number)
```

Спершу системні поля, далі прикладні. Аліаси прикладних — осмислена латиниця
(`name`, `code`, `edrpou`, `brand_ref`). Для поля-посилання, по якому фільтруватимуть,
виводь окремий аліас (напр. `дов.ПСТ_Бренд КАК brand_ref`). Для довідників типово
додавай `ГДЕ НЕ дов.ПометкаУдаления`.

Болванку роби через `generate_query` — він дає коректні системні поля й `source_name`.
Не відтворюй вручну: візьми болванку й допрацюй.

### Режими виконання .sel

Роутер `/1c/query` (`onec_router.py`) обгортає `.sel` у зовнішній `ВЫБРАТЬ`, щоб
застосувати проєкцію (`fields`), відбір (`filters`) і сортування (`order`). Режим
розпізнається автоматично.

**Режим 1 (типовий) — один `ВЫБРАТЬ`.** Роутер обгортає підзапитом
`ИЗ ( <текст .sel> ) КАК Вложенный`. `{fields}`, `{filters}`, `{order}` посилаються на
аліаси верхнього `ВЫБРАТЬ` — це публічний контракт виходу. Кілька пакетів (`;`) і
temp-таблиці (`ПОМЕСТИТЬ`) тут ЗАБОРОНЕНІ: 1С не дозволяє батч усередині дужок підзапиту.

**Режим 2 (пакетний, з temp-таблицями).** Коли потрібні тимчасові таблиці (напр.
`ИНДЕКСИРОВАТЬ ПО`, або той самий проміжний результат джойниться кілька разів) —
будь-яка кількість підготовчих пакетів, а фінальний обов'язково завершується записом
у службову `ТТ_РЕЗУЛЬТАТЗАПИТУ_`:

```
ВЫБРАТЬ ... ПОМЕСТИТЬ ТТ_Проміжна ИЗ ... ;

ВЫБРАТЬ
    Т.Номер       КАК Номер,
    Т.Контрагент  КАК Контрагент
ПОМЕСТИТЬ ТТ_РЕЗУЛЬТАТЗАПИТУ_
ИЗ ТТ_Проміжна КАК Т
```

Роутер доклеює фінальну проєкцію:
`ВЫБРАТЬ {fields} ИЗ ТТ_РЕЗУЛЬТАТЗАПИТУ_ ГДЕ {filters} УПОРЯДОЧИТЬ ПО {order}`.

Два обов'язкові правила Режиму 2:

1. **Завершуй саме на `ПОМЕСТИТЬ ТТ_РЕЗУЛЬТАТЗАПИТУ_`.** Без цього роутер піде
   звичайною гілкою і батч тихо зламається.
2. **Імена колонок `ТТ_РЕЗУЛЬТАТЗАПИТУ_` = публічний контракт виходу.** 1С будує рядки
   відповіді за іменами колонок, тож вони стають ключами JSON у `rows` і мусять
   збігатися з аліасами у `fields`. Інші імена → фронт мовчки отримає порожні поля.

Спільне для обох режимів: `offset`/`limit`/`total` застосовує роутер — **не роби їх у
`.sel`**; хвостовий `;` зрізається; коментарі `//` на початку рядка loader вирізає, а
хвостові в кінці рядка з кодом — ні (не лишай там `;`); параметри (`&search`) діють на
всі пакети; `fields` у `.json` лишай навіть у Режимі 2 — вона документує колонки виходу.

## Метадані й код конфігурації

`list_objects` віддає три форми залежно від конкретики запиту (лічильники → імена →
повна структура збігів). Нормалізація лікує різне НАПИСАННЯ (рос↔укр), але не різні
СЛОВА: `"пакунк"` не знайде `Упаковка`. Передавай варіанти масивом одразу —
`["пакунк","упаковк","відправлен","отправл"]`. Конфігурація змішана (рос. імена + укр.
синоніми), тож це норма, а не виняток.

`cf_module` — індекс вигрузки конфігурації: ~3470 модулів, ~67 500 процедур.
Читання коду безпечне, бізнес-даних не чіпає. `cf_find` — де **згадується**
(патерн: `match="contains"` + укр./рос. термін надійно знаходить модуль);
`cf_where` — де **оголошено**; `cf_search` — за префіксом імені; `cf_object_modules` →
`cf_module_toc` → `cf_body` — спуск від об'єкта до тіла; `cf_skeleton` — сигнатури без
тіл для god-модулів; `cf_top_modules`, `cf_meta` — орієнтація й свіжість.

**Не переказуй логіку BSL, не прочитавши тіло** через `cf_body`. Назва процедури й
здогад про неї — не її код.

## Запис даних 1С (save_cat / save_doc)

Пишуть у РЕАЛЬНІ довідники й документи — на відміну від решти write-інструментів, що
чіпають лише артефакти розробки.

- **`tabular_sections`**: кожна вказана ТЧ **ПОВНІСТЮ ПЕРЕЗАПИСУЄТЬСЯ** — старі рядки
  очищуються, потім додаються нові. ТЧ, відсутні в payload, не чіпаються. Неіснуюча
  назва → 400. Імена ТЧ і реквізитів бери з `describe_object`, не з пам'яті.
- **`version`** (ВерсіяДаних) з попереднього читання — оптимістичне блокування, щоб не
  затерти чужі зміни.
- **Атрибуція**: vps_api проставляє `Ответственный` за обліковкою MCP (`VPS_USERNAME`),
  тож документ буде за сервісним акаунтом, а не за реальним оператором. Якщо атрибуція
  важлива для задачі — це блокер, а не дрібниця.

## Фронтенд

Актуальний перелік файлів — `list_forms`. Компоненти (`html/components/`, лише
читання); точний API читай через `read_form` перед використанням:

- `ref_select.js` (RefSelect) — універсальний вибір посилання через `/1c/query`.
- `contractor_select.js` — пресет над RefSelect; вимагає `ref_select.js` ПЕРЕД ним.
- `doc_header.js` (DocHeader) — шапка документа (вид/номер/дата/статус/дії), сам
  інжектить CSS, класи `dh-`.
- `list_view.js` (ListView) — універсальний список (таблиця/картки), класи `lv-`.
- `confirm_modal.js` — `showConfirm(...)` → `Promise<boolean>`, `showAlert(...)` →
  `Promise<void>`. Підключати одразу після `auth.js`.

Глобали: `CONFIG.API_URL` (`lib/config.js`); `AUTH` (`lib/auth.js`) — `token`,
`username`, `role`, `userId`, `headers`, `logout()`. Немає або прострочений токен →
редірект на login.

**Як будувати форми:**

- Форма будується на ПОЛЯХ ЗАПИТУ (аліасах з `.json`), не на сирих реквізитах 1С.
- Скрипти — абсолютними шляхами (`/html/lib/config.js`, `/html/components/<...>`);
  спершу залежності (`ref_select.js`), потім пресети.
- Кеш: при зміні JS/CSS версіонуй (`?v=N`) — стара версія в кеші маскує правки й
  імітує «не працює».
- `getElementById` для guid-id — БЕЗ `CSS.escape` (ламає id з провідною цифрою).

**Дизайн** (єдина візуальна мова, з `list_view.css`; кольори захардкоджені, не
CSS-змінні): поверхня `#fff`, фон `#f5f6f8`/`#f0f2f5`, hairline `#e5e7eb`, текст
`#111827`, мутед `#9ca3af`/`#6b7280`, акцент `#2563eb`, світлий акцент `#eff6ff`,
виділення `#DBEAFE`, помилка `#DC2626`, успіх `#059669`. Радіуси 7–10px. Заголовки:
11px, uppercase, letter-spacing .4px, мутед. Мобільний брейк 600px (таблиця → картки).
Дата — `дд.мм.рррр`. Шрифт system-ui / Inter. Мінімум зайвого, службовий тон.

## Типові цикли

- **Новий запит:** `describe_object` → `generate_query` → допрацювати → показати
  користувачу → `save_query` → `log_command`.
- **Редагувати запит:** `get_query` → змінити ТІЛЬКИ потрібне → `save_query` →
  `log_command`.
- **Нова форма:** `read_form` кількох наявних (патерн) + `get_query` (поля) →
  згенерувати → `write_form` → `log_command`.
- **Дослідити логіку 1С:** `cf_find` → `cf_body`.

При редагуванні запиту передавай `file_name` = реальне ім'я файла (з `get_query.file`),
інакше створиться дубль — ім'я файла може відрізнятися від `query_name`.

## Журнал команд (html_command_log/)

Історія команд користувача (що, з якими уточненнями і чому надходило), щоб зберігати
контекст між чатами. Append-only, формат формує бекенд.

- `desc` — короткий ASCII-ідентифікатор: літери/цифри/дефіс/підкреслення, без пробілів
  і кирилиці (напр. `currency-form-green`). Українською — вміст полів, не ім'я файла.
- Тека входить у бекап `full_html` (`queries1c` + `html` + `html_command_log`). Свідомо
  приймаємо: відкат html-бекапу відкотить і журнал.

## Обмеження і політики

- `write_form` пише лише в `pages/` та `menu/`. `lib/`, `components/`, `system/` —
  тільки читання.
- Filesystem — тільки читання; запис на диск — виключно через MCP.
- Python-бекенд, `server.py` MCP-сервера і BSL 1С Claude не змінює — готує повний
  текст, застосовує користувач.
- Читання через `/1c/query` (іменовані запити) і `describe_object` (структура об'єктів,
  без даних) — дозволено вільно.
- `save_cat` і `save_doc` ЗАПИСУЮТЬ реальні бізнес-дані 1С. Claude НЕ використовує їх
  самостійно — ні для запису, ні для тестової перевірки контракту — без прямої вказівки
  користувача на кожну таку дію в поточному повідомленні. Одноразовий дозвіл не
  переноситься на наступні кроки чи сесії.
- `mcp_allowed` у метаданих запиту — свідоме обмеження доступу з боку користувача.
  Claude не встановлює й не змінює це поле самостійно, лише за прямою вказівкою.
- Не пиши секрети у файли `html/` (вони читаються через API).
- Нативні `alert()`/`confirm()`/`prompt()` у сторінках не використовуються — лише
  `showConfirm`/`showAlert` з `components/confirm_modal.js`.
- Зміна контракту API (серіалізація, імена полів) вимагає одночасної міграції всіх
  консументів — переліком, а не «потім довиправимо».
